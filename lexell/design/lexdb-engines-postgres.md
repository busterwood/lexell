## 1. Sort

**How tuples are held.** Each row becomes a `SortTuple` (`include/utils/tuplesort.h:148`): `{void *tuple; Datum datum1; bool isnull1; int srctape}`, which is 24 bytes. `datum1` holds the **first sort key's value**, so an int4/int8 key sits inline in the array and is compared without following the tuple pointer. The comment at `tuplesort.h:119-133` says: "Storing the first key column lets us save heap_getattr or index_getattr calls during tuple comparisons." `tuplesort_puttupleslot` (`backend/utils/sort/tuplesortvariants.c:751`) copies the slot into one palloc'd **MinimalTuple** (`ExecCopySlotMinimalTuple`) and extracts `datum1` once with `heap_getattr`.

**Memory contexts.** In PG 17 and later, the tuple copies of a non-bounded sort go into a **bump** context (`tuplesort_begin_batch`, `tuplesort.c:752`; `TupleSortUseBumpTupleCxt` at `tuplesort.h:109` checks for "not ALLOWBOUNDED"). The comment there says: "When the sort is not bounded, we make use of a bump.c context as this keeps allocations more compact with less wastage. Allocations are also slightly more CPU efficient." `utils/mmgr/bump.c` header: chunks have no chunk header, "it can fit more chunks on each block. This means we can do more with less memory and fewer cache lines." The `memtuples` array starts at 1024 or more entries and doubles (`grow_memtuples`, `tuplesort.c:1052`). The planner passes `CP_SMALL_TLIST` to the Sort's child (`optimizer/plan/createplan.c:2217,2248`), so only the needed columns (id, b) are copied, not the whole row.

**SortSupport.** At setup, `tuplesort_begin_heap` (`tuplesortvariants.c:180`) calls `PrepareSortSupportFromOrderingOp` once per key. The opclass then installs a raw C comparator: `btint4sortsupport` sets `ssup_datum_int32_cmp` (`access/nbtree/nbtcompare.c:215`) and `btint8sortsupport` sets `ssup_datum_signed_cmp` (`:299`). These comparators (`tuplesort.c:3139-3177`) are two-line `<`/`>` tests on Datums. `sortsupport.h` header: this replaces "repeatedly invoking an SQL-callable comparison function" through fmgr. If there is one key and no abbreviation, `onlyKey` is set (`tuplesortvariants.c:241`), so no tie-break call is ever made.

**Specialized qsorts (PG 15+).** `tuplesort.c:572-619` instantiates `include/lib/sort_template.h` five times: `qsort_tuple_unsigned`, `qsort_tuple_signed`, `qsort_tuple_int32`, `qsort_tuple` (runtime comparator) and `qsort_ssup`. `tuplesort_sort_memtuples` (`tuplesort.c:2676`) picks one by comparing the comparator **function pointer**. For example, if `sortKeys[0].comparator == ssup_datum_int32_cmp` it calls `qsort_tuple_int32`, whose comparator `qsort_tuple_int32_compare` (`:542`) is `pg_attribute_always_inline` and calls `ApplyInt32SortComparator` on `a->datum1`/`b->datum1`. The comment at `:482-489` says: "The goal is to try to sort two tuples without having to follow the pointers to the comparator or the tuple." `sort_template.h:321-333` also does a **presorted check**: one linear pass first, and if the input is already in order it returns with n-1 comparisons. It is Bentley-McIlroy quicksort with med3/ninther pivots for n > 40 and insertion sort for n < 7 (`:312-345`).

**Abbreviated keys (text, numeric).** In `varstr_sortsupport` (`utils/adt/varlena.c:1984`), under the C collation, the comparator becomes `varstrfastcmp_c` (memcmp). With abbreviation, the first 8 bytes of the string are memcpy'd into `datum1` (`varstr_abbrev_convert`, `:2348`) and compared with `ssup_datum_unsigned_cmp`, so `qsort_tuple_unsigned` is used. Abbreviation is turned off for non-C collations unless `pg_strxfrm_enabled` allows it (`:2038-2052`: "abbreviation for non-C collations is broken on many common platforms"). Cardinality is tracked with HyperLogLog, and abbreviation is aborted if it is not paying off (`varstr_abbrev_abort`, `consider_abort_common` at `tuplesort.c:1319`). For numeric, `numeric_sortsupport` (`utils/adt/numeric.c:2136`) converts the base-10000 digits into an int64 "excess-k" abbreviation (`numeric_abbrev_convert_var`, `:2390`). Neither applies to your two sort queries, whose keys are int4 (b) and int8 (c).

**Bounded heap sort (top-N).** `ExecSetTupleBound` (`executor/execProcnode.c:848`) pushes the LIMIT count into the Sort node, and `tuplesort_set_bound` (`tuplesort.c:838`) records it and **disables abbreviation** (`:867`: "Bounded sorts are not an effective target for abbreviated key optimization"). Tuples are appended normally until `memtupcount > bound*2` (`tuplesort_puttuple_common`, `:1219-1245`, "a heuristic for where heapsort becomes cheaper than a quicksort"). `make_bounded_heap` (`:2587`) then reverses the sort direction so the largest is at the root. From then on, each new tuple is compared once against `memtuples[0]` and, if not better, freed immediately (`TSS_BOUNDED` case, `:1272-1295`: "most input tuples can be discarded with just this one comparison"). Each input row is still copied into a MinimalTuple before that comparison (`tuplesort_puttupleslot` copies first), using an aset context, because bounded sorts must pfree. `sort_bounded_heap` (`:2636`) unheapifies in place at the end.

**External sort.** If `LACKMEM` is hit, tuples are quicksorted into runs and merged (balanced k-way merge since PG 15, file header `tuplesort.c:15-22`), and the merge uses a slab allocator (`init_slab_allocator`, `:1981`). Abbreviation is dropped for the merge (`mergeruns`, `:2024`).

**Incremental sort.** In `executor/nodeIncrementalSort.c`, if the input is already sorted on a prefix of the keys, PG sorts only within each prefix group, which is helpful mostly for LIMIT. It does not apply to your queries: neither `b` nor `c` has a presorted prefix, apart from an index on b, which gives full order **[inferred]**.

**Datum sort.** `ExecSort` (`executor/nodeSort.c:50`) uses `tuplesort_begin_datum` when the sort's result is **one column**, so no tuple is formed at all. It does not apply to `id, b`.

**What EXPLAIN would show** (**[inferred]** from `costsize.c`; please confirm with `EXPLAIN (ANALYZE, BUFFERS, SETTINGS)`):
- `select id, b from w order by b`: the planner estimates the sort input as `relation_byte_size = tuples * (MAXALIGN(width)+MAXALIGN(SizeofHeapTupleHeader))` (`optimizer/path/costsize.c:6453`), about 1M × 32 B = 32 MB. That is more than 4 MB of work_mem, so `cost_tuplesort` (`:1898`) costs a disk sort. At default work_mem, expect `Sort  Sort Key: b  Sort Method: external merge  Disk: ~20–30MB` over `Seq Scan on w`. If the benchmark raised work_mem, expect `Sort Method: quicksort  Memory: ...`. Because b is indexed, an `Index Scan using <b index>` is also possible: `cost_index` (`:560`) uses Mackert-Lohman `index_pages_fetched` (`:908`), and with the table fitting in `effective_cache_size` that caps heap fetches at roughly the table's page count × `random_page_cost`, then interpolates by `correlation²` (`:795-797`). Its total cost of about 85k can undercut seq scan + sort (100k+ CPU for the sort alone) **[inferred, arithmetic on default costs]**. With parallelism: `Gather Merge → Sort → Parallel Seq Scan`.
- `select id, b, name from w order by c desc limit 10`: `Limit → Sort (Sort Key: c DESC; Sort Method: top-N heapsort  Memory: ~25kB) → Seq Scan on w`. The string "top-N heapsort" is from `tuplesort_method_name` (`tuplesort.c:2543`). With parallelism: `Limit → Gather Merge → Sort (top-N in each worker) → Parallel Seq Scan`.
- The sort query costs more than `jit_above_cost=100000` (sort CPU alone ≈ 2×0.0025 × 1M × log2(1M) ≈ 100k), so JIT is probably on for the first query, but below 500k, so no inlining or -O3 **[inferred]**.

**Most plausible explanation of the gap (4050 vs 380 ms; 402 vs 90 ms).**
1. The leading int key lives **inline in a 24-byte array element**. The sort is `qsort_tuple_int32`/`_signed`, with the comparator inlined into the sort loop, no indirect call, no per-comparison dereference of the row, and no per-key closure. Compare lexdb's sortBy with a closure over arrays of refcounted values.
2. There is one contiguous MinimalTuple copy per row in a bump context, and no refcount traffic during the sort. For top-N, almost every row is rejected after **one** inline int8 comparison against the heap root.

## 2. DISTINCT and GROUP BY (HashAggregate)

- **Plan.** `select distinct city` and `group by city` become `HashAggregate` when the estimated number of groups fits in `hash_mem` (work_mem × 2). With parallelism: `Finalize HashAggregate → Gather → Partial HashAggregate → Parallel Seq Scan` **[inferred from standard planner behaviour]**.
- **Hash table.** `BuildTupleHashTable` (`executor/execGrouping.c:167`) builds a `tuplehash`, an instance of `include/lib/simplehash.h` (`execGrouping.c:35-44`). It is open addressing with linear probing (Robin Hood displacement). The `simplehash.h` header says: "Due to the 'templated' code generation has known structure sizes and no indirect function calls… Open addressing has better CPU cache behavior than dynahash's chained hashtables." An entry is `TupleHashEntryData {MinimalTuple firstTuple; uint32 status; uint32 hash}` (`include/nodes/execnodes.h:842`), which is 16 bytes. `SH_STORE_HASH` is on, so `SH_COMPARE_KEYS` (`simplehash.h:281`) compares the **stored 32-bit hash first** and calls the equality function only when the hashes match.
- **Hashing.** The hash is computed by a compiled ExprState, `ExecBuildHash32FromAttrs` (`executor/execExpr.c:4173`), using `EEOP_HASHDATUM_*` opcodes (`execExprInterp.c:1807-1900`) that call the type's hash function through a pre-bound `FmgrInfo`. `TupleHashTableHash_internal` (`execGrouping.c:421`) then applies `murmurhash32` (`include/common/hashfn.h:92`, a 5-instruction finalizer). Text uses `hashtext` (`backend/access/hash/hashfunc.c:270`): for a deterministic collation it is `hash_any(VARDATA_ANY(key), len)`, which is Bob Jenkins' lookup3 (`common/hashfn.c:30-41, hash_bytes :146`), fetching a word at a time when aligned. Int4 uses `hashint4 → hash_uint32` (`hashfunc.c:72`). PostgreSQL has no SipHash in core: `grep -ri siphash` finds only `pl/plperl/ppport.h`.
- **Key comparison.** `TupleHashTableMatch` (`execGrouping.c:520`) runs `ExecBuildGroupingEqual`'s ExprState, which for text is `texteq` (`utils/adt/varlena.c:1739`). Under a deterministic collation it compares **lengths first, then memcmp**, with no strcoll ("we can avoid all the expense of strcoll() here").
- **Per row.** `prepare_hash_slot` (`executor/nodeAgg.c:1203`) deforms the input only up to the largest group column and copies those Datums (pointers into the buffer page for text) into a virtual slot. `LookupTupleHashEntry_internal` (`execGrouping.c:469`) copies the tuple into the table **only for a new group** (`ExecCopySlotMinimalTupleExtra`), so the 1M rows that hit existing groups allocate nothing.
- **Aggregates.** Transition calls are compiled into one ExprState per phase (`ExecBuildAggTrans`, `execExpr.c:3709`), with specialized opcodes `EEOP_AGG_PLAIN_TRANS_{INIT_STRICT_,STRICT_,}{BYVAL,BYREF}` (`execExprInterp.c:2119-2240`). `count(*)` is a by-value int8 increment. `avg(numeric)` uses `do_numeric_accum` (`numeric.c:4982`). That reads the stored digits in place (`init_var_from_num`, a pointer assignment, `:7608`) and adds them into a `NumericSumAccum` (`:351-389`). The accumulator uses 32-bit digit slots so it "can safely accumulate up to NBASE - 1 values without propagating carry", and keeps separate positive and negative sums, so there is no per-row subtraction logic.

**Most plausible gap (DISTINCT 355 vs 90; GROUP BY 188 vs 130).**
1. The per-row work is: a lazy deform up to `city`, one lookup3 hash plus murmur finalizer, an open-addressing probe that compares a cached 32-bit hash before a length+memcmp, and **no allocation for existing groups**. DISTINCT in lexdb runs on the per-row path.
2. For `avg(price)`, PG's numeric is already binary base-10000 digits, so accumulation is a digit-array add with deferred carries. lexdb parses the decimal text on every read.

## 3. Tuple deforming and output

- **Heap scan.** `heapgettup_pagemode` (`access/heap/heapam.c:1012`) and `heap_prepare_pagescan` (`:556`) lock each page once. If `PageIsAllVisible` is set, `page_collect_tuples` (`:506`, instantiated with constant `all_visible=true`) skips the per-tuple visibility checks entirely and records the visible line pointers. Rows are then returned as **pointers into the pinned shared buffer**, with no copy (buffer-heap slot).
- **Lazy, partial deforming.** `slot_getsomeattrs(slot, n)` → `tts_buffer_heap_getsomeattrs` (`executor/execTuples.c:764`) → `slot_deform_heap_tuple` (`:1159`) decodes columns **only up to attribute n**, and is incremental: `tts_nvalid` remembers how far it got, and the next call resumes from the saved offset. Each compiled expression starts with an `EEOP_SCAN_FETCHSOME` step whose `last_var` is the highest column *that expression* references (`expr_setup_walker`, `execExpr.c:2992-3017`; opcode at `execExprInterp.c:660`).
- **attcacheoff.** `slot_deform_heap_tuple_internal` (`execTuples.c:1056`) is always-inline and instantiated for each `slow`/`hasnulls` combination ("allow the compiler to emit specialized versions"). Until the first NULL or the first varlena at an unaligned offset, every column's offset is read from `CompactAttribute.attcacheoff`, which is computed once per descriptor, so no offset arithmetic is needed. For `w(id int, a int, b int, c bigint, name text, …)` the first four columns, and `name`'s start, have cached offsets. Varlena values (text, numeric) become Datums that **point into the page**, so there is no copy and no refcount.
- **Slot types.** `TTSOpsVirtual` (just arrays of Datum/isnull, used for projection results), `TTSOpsMinimalTuple` (sort and hash outputs), and `TTSOpsBufferHeapTuple` (scan). Projections write into a virtual slot, so there is no tuple formation unless a consumer needs one.
- **Output.** `printtup` (`access/common/printtup.c:304`) calls `slot_getallattrs` and then, for each column, `OutputFunctionCall(&thisState->finfo, attr)`. The `FmgrInfo` for each column's output function is looked up once (`printtup_prepare_info`, `:250`) and reused for every row. The text goes through `pq_sendcountedtext` (`libpq/pqformat.c:142`), where `pg_server_to_client` is a no-op if the encodings match. The DataRow is built in a reused StringInfo, copied into the 8 KB `PqSendBuffer` (`libpq/pqcomm.c:119`), and the per-row context is reset once per row (`MemoryContextReset(myState->tmpcontext)`).
- **int4out** (`utils/adt/int.c:327`) does a palloc(12) and `pg_ltoa`. `pg_ultoa_n` (`utils/adt/numutils.c:1055`) gets the digit count with a bit trick (`decimalLength32`, `:45`: `(leftmost_one_pos+1)*1233/4096`) and emits **two digits at a time** from a 200-byte `DIGIT_TABLE`, four digits per loop.
- **numeric storage and output.** On disk a numeric is a varlena with a 2-byte header (`NumericShort`: sign, display scale, weight) followed by **int16 digits in base NBASE = 10000** (`utils/adt/numeric.c:57-160`). `numeric(10,2)` like 1234.56 is digits `[1234, 5600]`. `numeric_out` (`:816`) → `init_var_from_num`, which only points at the digits, → `get_str_from_var` (`:7651`), which divides each base-10000 digit by 1000/100/10 into 4 chars and does one palloc. There is no decimal parsing on read anywhere: arithmetic works on the stored digits.
- **Why `select *` costs PG about 250 ns per row [inferred breakdown, not measured].** It is not one big cost: page-mode scan and returning a buffer pointer (tens of ns), deforming all 9 columns (the first four with cached offsets, then the varlena walk), **9 fmgr output calls each with its own palloc** (3× int4out, int8out, 3× text_to_cstring copies, numeric_out with digit division, boolout), 9× strlen + appendBinaryStringInfo, a DataRow header, one context reset, and amortized `send()` per 8 KB. The relevant code is `printtup` and the type output functions above; a `perf` profile would be needed to split it.

**Most plausible gap (489 vs 250 for `select *`; it also feeds every other query).**
1. Deforming is lazy, stops at the last needed column, uses precomputed offsets, and produces zero-copy pointers into the page. lexdb decodes every column a level uses before conditions run, and materializes refcounted values.
2. For numeric, PG never parses text on read: storage is base-10000 binary and output formats 4 digits per stored digit.

## 4. Expression evaluation

- **Interpreter.** In `executor/execExprInterp.c`, the header says expressions are a flat array of `ExprEvalStep`s, run with **direct threading** (computed goto, `EEO_USE_COMPUTED_GOTO` at `:89`). `ExecReadyInterpretedExpr` replaces each opcode with the address of its code block, which gives "better branch prediction (as the jumps are happening from different locations) and fewer jumps". Column references compile to `EEOP_SCAN_VAR`/`INNER_VAR`/`OUTER_VAR`: an array index into `tts_values[attnum]` (`:717`), by **attribute number resolved at plan time** (no name lookup). Projections of plain columns become `EEOP_ASSIGN_SCAN_VAR` (`execExpr.c:462,738`).
- **Fast paths.** Very short expressions bypass the interpreter loop entirely through `ExecJust*` functions (`execExprInterp.c:157-176`): `ExecJustScanVar`, `ExecJustAssignScanVar`, `ExecJustConst`, `ExecJustHashOuterVar` and so on, plus `*Virt` variants for virtual slots.
- **Qual short-circuit.** `ExecInitQual` (`execExpr.c:229`) emits an `EEOP_QUAL` after each conjunct (`execExprInterp.c:1180`). On false or NULL it jumps straight to the end ("simplified version of BOOL_AND_STEP… As qual evaluation is a hot-path this warrants using a special opcode").
- **Function calls.** `ExecInitFunc` (`execExpr.c:2711`) does `fmgr_info` **once at executor startup** and caches `fn_addr` in the step ("Keep extra copies of this info to save an indirection at runtime"). Argument expressions are compiled to write directly into `fcinfo->args[i]`. **Const arguments are stored into fcinfo once and never re-evaluated** ("Don't evaluate const arguments every round; especially interesting for constants in comparisons"). Strict functions with 1 or 2 arguments get dedicated opcodes `EEOP_FUNCEXPR_STRICT_1/_2` (`execExprInterp.c:994`): a NULL check and one indirect call. So `a = 5` is roughly FETCHSOME, SCAN_VAR, FUNCEXPR_STRICT_2(int4eq), QUAL, DONE.
- **Per-row memory.** Every pass-by-reference result (numeric, text) is palloc'd in the per-tuple ExprContext, which is reset with `ResetExprContext` once per row (`include/executor/execScan.h`, `ExecScanExtended`). That is a pointer bump, no frees and no refcounts.
- **LIKE.** `textlike` → `GenericMatchText` (`utils/adt/like.c:150`) picks `UTF8_MatchText`, a specialization of `like_match.c` where NextChar skips continuation bytes. In `MatchText` (`like_match.c:80`): `%` alone returns TRUE at once. For `%literal…`, it skips wildcards and then **scans the text byte by byte for the first literal byte**, recursing only on a byte match (`:150-176`), and returns `LIKE_ABORT` to stop outer scans early. There is no memmem/SIMD and no pattern precompilation; the pattern is a Const, so it is passed once. Byte-wise comparison is valid for UTF-8 under deterministic collations (`:94-101`). `note` is the 9th column, so this query deforms the whole row for every tuple.
- **upper().** `upper` (`utils/adt/oracle_compat.c:80`) → `str_toupper` (`utils/adt/formatting.c:1704`). If the collation's ctype is C, it is `asc_toupper`, a byte loop. Under a libc UTF-8 locale, `strupper_libc_mb` (`utils/adt/pg_locale_libc.c:373`) palloc's a wchar_t buffer, runs `char2wchar` (mbstowcs), calls `towupper_l` per character, mallocs the result, runs `wchar2char`, memcpy's, and frees twice. That is **several allocations and two encoding conversions per call**, so it is not cheap in PG either. The collation lookup is cached (`pg_newlocale_from_collation`, `pg_locale.c:1196`, `last_collation_cache_oid`).
- **Numeric multiply.** `numeric_mul` (`numeric.c:3128`) → `mul_var` (`:8826`). If the shorter operand has at most 6 base-10000 digits and the exact result is requested, it delegates to `mul_var_short` (`:9117`), "a faster direct multiplication algorithm". Here `price * 2` is a 2-digit × 1-digit multiply on the stored digits. The constant `2` is coerced to numeric once at plan time (constant folding), and `make_result` palloc's the result in the per-tuple context. `a + b` is `int4pl` with overflow checking via a single `FUNCEXPR_STRICT_2`.
- **JIT.** It is on by default (`jit = on`), with `jit_above_cost = 100000` (`jit/jit.c:39`), and is applied in `standard_planner` when `top_plan->total_cost > jit_above_cost` (`optimizer/plan/planner.c:610-624`). It compiles expressions (`PGJIT_EXPR`) and tuple deforming (`PGJIT_DEFORM`). `llvmjit_deform.c` header: "gains performance benefits over unJITed deforming from compile-time knowledge of the tuple descriptor. Fixed column widths, NOT NULLness, etc". The default plan for a 1M-row seq scan with a simple projection costs roughly 25–40k (pages + 1M × cpu_tuple_cost), which is **below** the threshold. The 1M-row sort and the 1M × 1M join are probably above it. Inlining and -O3 need 500k **[inferred estimate; check with EXPLAIN ANALYZE, which prints a "JIT:" section when used]**.

**Most plausible gap (1583 vs 340 for the projection query).**
1. Expressions are flat step arrays with computed-goto dispatch, columns are referenced by attnum in a Datum array, functions are bound once with constants pre-loaded, and temporaries are bump-allocated and reset per row. lexdb uses a tree walk with column lookup by name.
2. `price * 2` works directly on base-10000 digits (`mul_var_short`). lexdb parses the decimal text first.

## 5. Filters

- `ExecScanExtended` (`include/executor/execScan.h:160`): for each tuple it calls `ExecQual(qual)` **first** and only calls `ExecProject` if the qual passes (`:223-241`). Rejected rows reset per-tuple memory and loop. PG 18 adds specialized node entry points so the "no qual"/"no projection" branches are compiled out: `ExecSeqScan`, `ExecSeqScanWithQual`, `ExecSeqScanWithProject` and `ExecSeqScanWithQualProject` (`executor/nodeSeqscan.c:110-190`, chosen at `:265-277`).
- **Yes, deforming is lazy across qual and projection.** The qual and the projection are *separate* ExprStates, each with its own `FETCHSOME` (`ExecInitQual` at `execExpr.c:250` and `ExecBuildProjectionInfo` at `:392` both call `ExecCreateExprSetupSteps`). For `where a = 5`, the qual's FETCHSOME deforms columns 1–2 only. Only for the ~1% of rows that pass does the projection's FETCHSOME continue, from the saved offset, to column 5 (`name`). The 99% of rejected rows never touch `name`, `note` and the rest.
- If the page is all-visible, rows reach the qual with no visibility work (§3).

**Most plausible gap (71 vs 40; 136 vs 80 for LIKE).**
1. The qual runs on columns decoded up to the highest attribute it uses, and nothing else is decoded for rejected rows. lexdb decodes every column the level uses before any condition runs.
2. The LIKE query is closer, because PG must also deform through column 9 for every row and runs a scalar byte scan, so the remaining difference is mostly per-row overhead **[inferred]**.

## 6. Hash join

- **Layout** (`include/executor/hashjoin.h`). The table is an array of `nbuckets` bucket heads (a power of two). Each entry is a `HashJoinTupleData {next pointer; uint32 hashvalue}` followed immediately by the MinimalTuple (`:78-92`). Entries are carved out of **32 KB chunks** by `dense_alloc` (`executor/nodeHash.c:2896`; `HASH_CHUNK_SIZE` at `hashjoin.h:150`; tuples above 8 KB get their own chunk), which avoids palloc per tuple and keeps the tuples dense. The target load is `NTUP_PER_BUCKET 1` (`nodeHash.c:655`); `ExecChooseHashTableSize` (`:658`) sizes the table from planner estimates, and `ExecHashIncreaseNumBuckets` resizes after the build if the estimate was wrong.
- **Build.** `MultiExecPrivateHash` (`nodeHash.c:138`) pulls every inner tuple in a tight loop. It evaluates the compiled hash ExprState once per tuple (`ExecEvalExprSwitchContext(node->hash_expr…)`), then calls `ExecHashTableInsert` (`:1749`). That does `ExecFetchSlotMinimalTuple`, memcpy into the dense chunk, **stores the 32-bit hash in the entry**, and pushes the entry onto the bucket list. Bucket = `hash & (nbuckets-1)`; batch = the rotated high bits (`ExecHashGetBucketAndBatch`, `:1960`). The inner child is planned with `CP_SMALL_TLIST` (`createplan.c:4945`), so only the join key and needed columns are copied.
- **Probe.** `ExecHashJoinOuterGetTuple` (`executor/nodeHashjoin.c:979`) computes the outer hash once (`hj_OuterHash` ExprState). `ExecScanHashBucket` (`nodeHash.c:1992`) walks the bucket and **compares `hashTuple->hashvalue == hashvalue` before** running the join-clause ExprState, so hash collisions in a bucket rarely run `texteq`. Semi joins and inner-unique joins set `single_match` (`nodeHashjoin.c:781`) and stop at the first match.
- **Text hashing.** `hashtext` → `hash_any` (lookup3, `common/hashfn.c`) for deterministic collations. There is no SipHash and no per-table random key; the parallel worker IV is only used for hash aggregation (`execGrouping.c:221`).
- **Skew optimization.** `ExecHashBuildSkewHash` (`nodeHash.c:2403`): if the *outer* side's join key has MCV statistics, inner tuples matching the top MCVs' hash values go into a separate skew table, limited to 2% of memory (`SKEW_HASH_MEM_PERCENT`, `hashjoin.h:121`). Outer tuples with those hash values never go to batch files. It only matters when the join is multi-batch.
- Memory is `work_mem × hash_mem_multiplier` = 8 MB by default. More than that means multiple batches, with temp files written per batch.

**Most plausible gap (text-key join 112 vs 80).**
1. The inner side is built once into dense chunks with the hash stored per entry. Each outer row costs one lookup3 hash over a pointer into the page, a masked bucket index and a 32-bit hash compare. lexdb reads and hashes the hashed table row by row at about 550 ns per row and uses SipHash.
2. The outer side is the batch-free tight `ExecProcNode` loop with lazy deform of only the key column. The remaining 80 ms is mostly the 1M-row outer scan, so the build side is not the issue here.

## 7. Merge join and the 1M × 1M join (`w join t on t.id = w.b`, count)

- **[inferred] likely plan.** `Aggregate → Merge Join (Merge Cond: w.b = t.id) → Index Only Scan using <b index> on w` and `→ Index Only Scan using t_pkey on t`. Both inputs come out of the indexes already in key order, so there is no sort, and `count(*)` needs only the key columns, so both scans can be index-only. The alternative, `Hash Join` with t (1M rows) hashed, would need about 40+ MB of hash table against an 8 MB hash_mem, so multiple batches with temp-file I/O. `cost_index` lowers heap cost for index-only scans by `(1 - allvisfrac)` (`costsize.c:696-747`), which makes the merge-join path cheap when the visibility map is set. 70 ms for 2M index tuples, about 35 ns each, fits index-only scans better than a multi-batch hash join. `EXPLAIN` will show which one, and `Heap Fetches:` shows whether the visibility map was set.
- **Merge join comparison.** `MJExamineQuals` sets up SortSupport for each merge clause (`executor/nodeMergejoin.c:213-257`; abbreviation is off). `MJCompare` (`:386`) calls `ApplySortComparator`, which for int4 is `ssup_datum_int32_cmp`. Because `t.id` is unique, the planner sets `skip_mark_restore` (`:1481-1485`), so the inner side needs no mark/restore.
- **Index-only scan and visibility map.** `IndexOnlyNext` (`executor/nodeIndexonlyscan.c:62`): for each index TID, `VM_ALL_VISIBLE(heapRel, block)` (`:162`) is checked. If set, the heap is **not visited at all** and the value is taken from the index tuple. The visibility map bit is set by VACUUM (including autovacuum after a bulk load). The same comment block (`:147`) notes "Deletes do not update the index page (only VACUUM will clear out the TID)".
- **Leaf batching.** `_bt_readpage` (`access/nbtree/nbtsearch.c:1649`) copies **all matching items on a leaf page** into `so->currPos.items` while holding the page lock once. `_bt_next` then hands them out without touching the page again, and moves to the next leaf by sibling link (`_bt_steppage`, `:2169`) with no re-descent.

**Most plausible gap (585 vs 70).**
1. PG probably does no hashing at all: it merges two pre-ordered index-only scans with an inline int compare. lexdb hashes 1M rows at about 550 ns each, which alone is about the whole lexdb time.
2. The visibility map lets those scans skip the table entirely.

## 8. B-tree

- **Page layout.** This is the standard slotted page: an array of 4-byte `ItemId` line pointers (offset, length, flags) at the start, and tuples packed from the end. Binary search indexes the line-pointer array, so variable-length keys are found by indirection, not scanning. `IndexTuple` = TID + null/varwidth flags + key datums; duplicates are compressed into posting lists (`nbtdedup.c`).
- **Descent.** `_bt_search` (`nbtsearch.c:107`) goes from the root (the metapage is cached in relcache `rd_amcache`) through `_bt_binsrch` (`:348`) on each internal page down to the leaf. `_bt_binsrch` is a plain binary search over line pointers calling `_bt_compare` (`:693`). `_bt_compare` calls `index_getattr` (cached offsets for fixed-width leading keys) and then `FunctionCall2Coll(&scankey->sk_func, …)`, i.e. **`btint4cmp` through fmgr** (`nbtcompare.c:201`). That is an int compare of two int32 Datums behind one indirect call. There is no memcmp of an encoded key; the int is compared as an int.
- **Sort support.** Sorts and merge joins use `btint4sortsupport → ssup_datum_int32_cmp` (no fmgr). The B-tree search itself still uses the fmgr comparator.
- **Insert fastpath.** For increasing keys, the backend caches the rightmost leaf and skips the descent (`nbtree/README`, "Fastpath For Index Insertion", line 492; `BTREE_FASTPATH_MIN_LEVEL` in `nbtinsert.c:30`).
- **Index scan vs bitmap heap scan for `b > 90000` (100k rows).**
  - *Plain Index Scan*: for each matching TID, `heapam_index_fetch_tuple` (`access/heap/heapam_handler.c:115`) calls `ReleaseAndReadBuffer` (`storage/buffer/bufmgr.c:3032`). If the TID is on the **same heap block as the previous one, the pinned buffer is reused** with no hash lookup ("does save considerable work"). Otherwise it does one buffer-mapping hash lookup. The **TID is a direct (block, offset) address, so there is no second B-tree descent** to fetch the row. Heap fetches = number of matching index entries, but the number of distinct pages touched depends on how correlated b is with the physical order.
  - *Bitmap Heap Scan*: a Bitmap Index Scan collects TIDs into a `TIDBitmap` (`nodes/tidbitmap.c`) keyed by page. The heap is then read **in block order, each page once**, with page-at-a-time visibility (`BitmapHeapNext`, `executor/nodeBitmapHeapscan.c:126`; read-stream prefetch, `heapam.c:314`). It becomes lossy (page-level, with recheck) if it exceeds work_mem.
  - *Planner costing*: `cost_index` (`costsize.c:560`) interpolates between `max_IO_cost` (uncorrelated: Mackert-Lohman pages × `random_page_cost`) and `min_IO_cost` (correlated: 1 random page + sequential pages) by **correlation²** (`:795-797`), plus `cpu_index_tuple_cost + cpu_operator_cost` per index entry and `cpu_tuple_cost` per heap tuple. `cost_bitmap_heap_scan` (`:1023`) and `compute_bitmap_pages` (`:6514`) estimate distinct pages. For 10% selectivity on an uncorrelated column, a bitmap scan or even a seq scan with filter usually wins. For a correlated column, the plain index scan wins **[inferred]**.

**Most plausible gap (index range 167 vs 30).**
1. A heap fetch in PG is a direct TID address: same-page fetches reuse the pinned buffer, and other pages cost one hash lookup. lexdb does a full primary-key B+tree descent per index entry, with memcmp on encoded keys at each level.
2. Leaf items are batched per page (`_bt_readpage`), and if the planner chose a bitmap scan, each heap page is visited once in physical order.

## 9. Subqueries (IN, EXISTS)

- **Pull-up.** `pull_up_sublinks` (`optimizer/prep/prepjointree.c:484`) → `convert_ANY_sublink_to_join` (`optimizer/plan/subselect.c:1346`) turns `a IN (select k from d where grp=3)` into a `JoinExpr` with `jointype = JOIN_SEMI` (`:1442`). `convert_EXISTS_sublink_to_join` (`:1463`) does the same for a correlated `EXISTS` (`JOIN_SEMI`, or `JOIN_ANTI` for NOT EXISTS, `:1598`), turning the correlation `d.k = w.a` into the join qual. So **both of your queries become the same ordinary join plan**, with no per-row subplan.
- The join planner then considers a plain semi join (Hash Semi Join, which stops at the first match via `single_match`), `JOIN_UNIQUE_INNER` (unique-ify d.k with a HashAggregate, then a plain inner join, `optimizer/path/joinpath.c:184`), and PG 18's `JOIN_RIGHT_SEMI` (`include/nodes/nodes.h:315`, `nodeHashjoin.c:538,789`, which hashes the *outer* relation and emits each inner match once). **[inferred] likely plan:** `Aggregate → Hash Join / Hash Semi Join (w.a = d.k) → Seq Scan on w; Hash → Seq Scan on d (Filter: grp = 3)`, with the tiny d side hashed and w probed once per row through the machinery in §6.
- **When not pulled up** (e.g. under OR, or in a target list), an uncorrelated `IN` becomes a **hashed SubPlan**: `buildSubPlanHash` (`executor/nodeSubplan.c:476`) loads the subquery result into a `TupleHashTable` (§2) once, and `ExecHashSubPlan` (`:101`) probes it per row with `FindTupleHashEntry`. A correlated SubPlan that is not pulled up is rerun per outer row (`ExecScanSubPlan`, `:203`). Core has no SubPlan memoisation; the Memoize node caches parameterized nested-loop inner scans instead.

**Most plausible gap (488 and 617 vs 50).**
1. Both forms are rewritten at plan time into a semi join, so the per-row work is one int hash probe on a tiny table inside a tight scan loop with lazy deform of `a` alone. lexdb runs IN and EXISTS on the per-row path, with the full per-row expression overhead.
2. EXISTS gets no special cost in PG: after pull-up it is identical to IN.

## 10. Window functions (`row_number() over (partition by a order by c) where a < 20`)

- **[inferred] plan.** `WindowAgg → Sort (Sort Key: a, c) → Seq Scan on w (Filter: a < 20)`. The sort's leading key is int4, so `qsort_tuple_int32` runs, with `comparetup_heap_tiebreak` (`tuplesortvariants.c:1260`) on `c` only when the `a` values tie. In PG 18, EXPLAIN prints the window clause as `ROWS UNBOUNDED PRECEDING`, because `window_row_number_support` (`utils/adt/windowfuncs.c:98-127`) answers `SupportRequestOptimizeWindowClause` by rewriting the frame to `ROWS BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW` ("Using ROWS instead of RANGE saves effort checking peer rows during execution").
- **Execution.** `ExecWindowAgg` (`executor/nodeWindowAgg.c:2225`) consumes sorted input. `begin_partition` (`:1208`) and `spool_tuples` (`:1297`) append input rows to a per-partition **tuplestore** (`tuplestore_puttupleslot`, `:1377`), detecting the partition boundary with a compiled equality ExprState on `a` against `first_part_slot` (`partEqfunction`, `:1358`). Peer groups are checked by `are_peers` (`:3190`) only when the frame or function needs them; row_number does not after the rewrite.
- `window_row_number` (`windowfuncs.c:84`) is three lines: `WinGetCurrentPosition`, `WinSetMarkPosition` (lets the tuplestore trim rows already read), and return `curpos + 1`. The function itself costs almost nothing; the cost is the sort plus one tuplestore write and read per row.

**Most plausible gap (948 vs 130).**
1. The sort underneath uses the inline-int32 specialized qsort (§1).
2. The window evaluation is a compiled partition-equality check plus a near-free row_number on a mark-trimmed tuplestore. lexdb runs window functions on the per-row path.

## 11. DML

- **INSERT … SELECT.** `ExecInsert` → `table_tuple_insert(rel, slot, cid, 0, NULL)` (`executor/nodeModifyTable.c:1233`) is called **with a NULL BulkInsertState**. Only COPY (`commands/copyfrom.c:370,1090`), CTAS (`commands/createas.c:568`), matview refresh and table rewrite use `GetBulkInsertState()`. `ExecBatchInsert` exists only for FDWs (`ri_BatchSize = 1` for heap). So INSERT … SELECT is row by row: `heap_insert` (`access/heap/heapam.c:2083`). Even so, `RelationGetBufferForTuple` (`access/heap/hio.c`) first tries the relation's **cached target block** (`RelationGetTargetBlock`, `:579`), so consecutive inserts land on the same page without an FSM lookup. When it extends, `RelationAddBlocks` (`:241`) extends by more pages when there are lock waiters. Each row then gets one `XLOG_HEAP_INSERT` WAL record holding the tuple (`xl_heap_insert`, `include/access/heapam_xlog.h:166`) and one `ExecInsertIndexTuples` per index (`nodeModifyTable.c:1239`). The B-tree uses the rightmost-leaf fastpath for increasing keys (§8). COPY instead uses `heap_multi_insert`, one WAL record for many tuples.
- **DELETE: index entries are not touched. Confirmed.** `ExecDeleteAct` (`nodeModifyTable.c:1507`) is only `table_tuple_delete(...)` → `heap_delete` (`heapam.c:2832`). That sets `xmax` and infomask bits on the heap tuple and writes one small `XLOG_HEAP_DELETE` record (`xl_heap_delete` is `{xmax, offnum, infobits_set, flags}`, `heapam_xlog.h:116`; `XLogInsert` at `heapam.c:3208`). There is no call into any index AM. The row to delete is located by its **TID** (the ctid junk column from the scan), not by a key lookup. The sources that confirm index entries are left behind:
  - `nodeIndexonlyscan.c:147`: "Deletes do not update the index page (only VACUUM will clear out the TID)".
  - `access/heap/README.HOT`, "Technical Challenges": finding and removing index entries per tuple is "normally impractical"; VACUUM amortizes the index scan "across as many dead tuples as possible".
  - `access/nbtree/README`, "Simple deletion" (line 511): later index scans that find a dead heap tuple set `LP_DEAD` on the index item ("like a hint bit"), and those items are physically removed only when a leaf page would otherwise split. "Bottom-Up deletion" (line 557, added in PG 14) removes version-churn duplicates on a leaf page, again only when the page is about to split. "Deleting index tuples during VACUUM" is at line 166.
- **UPDATE and HOT.** `heap_update` computes `modified_attrs` against the indexed columns (`hot_attrs`, `heapam.c:3413-3509`). If the new version fits on the **same page** and **no indexed column changed** (`if (newbuf == buffer) … if (!bms_overlap(modified_attrs, hot_attrs)) use_hot_update = true`, `:4133-4142`), the new tuple is heap-only and `ExecUpdateEpilogue` skips index insertion (`updateIndexes == TU_None`, `nodeModifyTable.c:2337`). Otherwise new index entries are inserted, and old ones are again left for VACUUM or deletion. `README.HOT` describes the scheme and its single-page pruning (`heap_page_prune_opt`, called opportunistically from scans).
- **WAL per row.** One heap record per inserted, deleted or updated tuple, plus one per index insertion. There is a full-page image on the first touch of a page after a checkpoint (`full_page_writes = on`). Records are memcpy'd into shared WAL buffers, and with `synchronous_commit = on` there is **one WAL flush per commit**, not per row.

**Most plausible gap.**
1. DELETE with an index (4390 vs 50 ms): PG does **zero index work at delete time**. It marks xmax on a tuple it already found by TID and writes a ~10-byte WAL record. lexdb deletes each index entry immediately.
2. INSERT, UPDATE and the no-index DELETE: there is one heap write to a cached target page and one small WAL record per row, and on UPDATE, HOT skips index maintenance when no indexed column changes. Note that PG does **not** use bulk-insert state for INSERT … SELECT, so that is not the source of its speed there.

## 12. Parallel query

- **Eligibility.** `standard_planner` (`planner.c:380-407`) allows parallel mode only for `CMD_SELECT` without modifying CTEs, when `max_parallel_workers_per_gather > 0`. **INSERT/UPDATE/DELETE never get parallel plans** (CTAS, SELECT INTO and matview refresh may; see the comment there).
- **Worker count.** `compute_parallel_worker` (`optimizer/path/allpaths.c:4468`): a relation smaller than `min_parallel_table_scan_size` (8 MB = 1024 pages) gets 0 workers. Otherwise it gets 1 worker plus one more for each ×3 of size (≥3072 pages → 2, ≥9216 → 3 …), capped by `max_parallel_workers_per_gather = 2`. A 1M-row `w` of about 100+ MB gets the cap of 2 workers plus the participating leader (`parallel_leader_participation = on`), i.e. about 3 processes **[inferred size]**.
- **Cost gates.** `parallel_setup_cost = 1000` per Gather, and `parallel_tuple_cost = 0.1` per row passed from worker to leader. So shapes that **return few rows** (counts, aggregates, top-N, DISTINCT with few groups, 1% filters) parallelize. Shapes that return 1M rows (`select *`, the 4-column projection, the full `order by b`) mostly do not, because 1M × 0.1 = 100k extra cost. That is consistent with your "PG parallel" column being no faster for those.
- **Parallel node types.**
  - Parallel Seq Scan: workers claim block ranges (`ExecSeqScanInitializeDSM`, `nodeSeqscan.c:361`).
  - Partial and Finalize Aggregate, including HashAggregate (per-worker hash IV via `murmurhash32(ParallelWorkerNumber)`, `execGrouping.c:221`).
  - Parallel Hash Join, where workers build one shared hash table (`MultiExecParallelHash`, `nodeHash.c:219`; `enable_parallel_hash = on`); or a parallel-oblivious Hash Join, where each worker builds its own copy of the small inner side (e.g. the 20-row `cr` and the filtered `d`).
  - Gather Merge over per-worker Sorts (top-N bounded heaps in each worker).
  - Parallel Index (Only) Scan when the index is at least `min_parallel_index_scan_size` = 512 kB.

**Most plausible gap (aggregates and filters about 2× faster in parallel).** With defaults, every 1M-row scan that returns few rows runs on about 3 processes (2 workers + leader) with per-worker partial aggregation or top-N. lexdb is single-threaded by design. For the shapes returning 1M rows, PG's single-core numbers are the relevant comparison.
